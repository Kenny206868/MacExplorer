# Dual-pane workspace design and interaction contract

The native interface, not an HTML view embedded in the app, is the product. Keep the original palette, 48/54/54-point top chrome, fitted Details columns, restrained separators and a single shared sidebar. Extend that design with two real file browsers inside the file area: each has its own location, history, selection, query and view options. The global tab strip remains the window's tab collection; a pane's tab picker chooses which tab it presents. Focus and pane assignment are separate concepts.

An active pane uses a narrow accent indicator and a visible Active label. Do not dim inactive file names or hide their selections. Shared sidebar, commands, inspector, path and search follow the active pane. Switching focus must not refresh away selections or cancel an in-flight transfer. Narrow windows stack the two panes vertically without discarding either pane or rewriting the preferred orientation. Hide auxiliary previews responsively only when dual-pane space requires it; preserve user intent.

Provide explicit Copy to Other Pane and Move to Other Pane buttons, with destination shown and move confirmation. Cmd/Ctrl+Shift+D toggles dual panes, Tab switches active file panes only when focus is in a file surface, Cmd/Ctrl+Shift+C copies to the other pane and Cmd/Ctrl+Shift+M asks to move. F5 remains Refresh, rather than silently acquiring a destructive commander-style meaning. F6 cycles location/search/files. Arrow, Home/End, Page Up/Down, Shift range, Ctrl focus-only, Ctrl+Space and type-to-select share the same selection model in all views. Text editors and open sheets keep their own keys.

Each file surface must receive file URLs and native promises using its own destination captured at drop time. Dragging from an inactive pane activates that source before resolving selection; hovering the destination must not mutate the source selection. An external drag never causes this app to delete the source based only on a returned drag mask.

Trackpad swipe navigates history, pinch changes icon density, and ordinary two-finger scrolling stays native. Touch-friendly mode increases file rows and file-surface action targets to 44 points and supplies explicit selection/open/context actions without requiring hover or modifier keys. This is a macOS application: direct multitouch behavior depends on the device/driver delivering supported AppKit input, not on an invented iPad compatibility layer.

CI must capture populated light/dark dual panes, both orientations, narrow fallback, touch-friendly density and focus changes. Test actual command routing, per-pane operation targets, selection preservation and session restoration, not just nonblank bitmaps. Alpha binaries and their galleries must originate from the same successful commit. PNG capture and palette checks use explicit sRGB, not an untagged DeviceRGB bitmap.
