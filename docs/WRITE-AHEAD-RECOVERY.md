# Write-ahead recovery in the file engine

Every engine copy/move/install/replacement, merge child, rename cycle, create, compress and extract now records its filesystem intent in SQLite WAL before the mutation. The engine serialization gate spans collision awaits. A completed item's inverse receipt is checkpointed before moving to the next item. Recovery compensates only the suffix after that durable checkpoint; already completed work remains completed.

Private destination staging is registered before creation. Data copies are synchronized before installation. Renames use pinned parent descriptors, no-follow identity checks and exclusive destination semantics. Cross-volume moves retain the original object in a hidden recovery location on its original volume after the synchronized destination is installed; they do not delete the only original copy to emulate an atomic cross-volume rename. Merge source containers and replacement backups remain reversible.

Undo checkpoints contain both the inverse receipt and the original receipt's remaining steps in one SQLite update. Receipt replay uses SQLite insertion order, not wall-clock order. Native Trash and permanent deletion have intent/outcome records, but their OS execution cannot be made atomic with a separate database. A crash with an unknown native outcome is an explicit review item, never silently repeated or guessed.

The Recovery & history panel distinguishes interrupted transactions from completed Undo records. Safe recovery checks recorded identities and destination vacancies. Explicit Keep Current Files acknowledgement retains the audit record and performs no compensation. Retained staging is revealed for inspection, not recursively deleted after restart just because its path appears in a journal. Unreviewed interrupted work blocks new mutations.

`FileOperationCrashProbe` runs the actual engine in disposable subprocesses and exits without Swift cleanup at intent, filesystem-applied, applied-record, and checkpoint boundaries. The suite covers replacement, copy/move, create, rename cycles and interrupted Undo. `ExplorerJournalTests` separately covers WAL recovery, locking, malicious path changes, active compensation, and acknowledgement. Run both suites on macOS; Linux journal tests alone do not validate AppKit or the macOS copy engine.

Durability is conditional on filesystem and storage guarantees. SQLite FULL synchronization and available filesystem flushes are requested, not a claim that arbitrary network volumes, device firmware or every power-loss scenario are certified. File metadata edits and external provider APIs remain separately scoped; native operations with unknowable outcomes require review. Production signing secrets and physical assistive/input-device evaluations are not supplied by this software test suite.
