# Native design and dual-pane alpha track

The native SwiftUI application now uses the original design's palette, explicit pane sizing, fitted Details columns, Home cards and redesigned inspector. Dual mode gives both independent browsers their own visible tabs, address editor, ancestor menu and search. The shared transfer bar makes source and destination explicit. Responsive stacked fallback preserves preferred orientation and selections; touch-friendly mode uses larger file rows and action targets.

All five Settings pages use the same native design system. Single-file renaming is in-place with extension-aware UTF-16 selection; multiple-file renaming retains its preview dialog. Details marquee selection supports edge scrolling, and collapsed groups cannot retain hidden actionable keyboard selections. Tab transfer uses one-shot in-process tickets and preserves the live tab object. New-window detachment retains the source until the target acknowledges arrival; automatic mouse-release detection is conservative and still requires hardware evaluation.

Menu and keyboard file commands share a modal safety boundary across both panes. Text editing remains native; Control–Option is reserved for VoiceOver. Cross-pane transfer shortcuts use Command–Option–C/M, with explicit buttons as alternatives. Gesture and touch availability depends on macOS and input hardware rather than an invented iPad compatibility layer.

The current native visual contract contains **78 captures on each of macOS 15 Intel and macOS 26 Apple Silicon**. It includes populated reference views, dual orientations, independent tab/selection state, narrow and touch layouts, file actions, keyboard help, settings, archive browsing and actual in-place filename editing. Every published alpha carries matching source, native ZIP/DMG, PNG galleries, toolchain evidence and checksums from the exact successful commit. The native tests check geometry, palette, edit focus/selection and operation behavior in disposable directories; they are not a claim of complete Windows/Finder equivalence or a finished hardware accessibility audit.

Development alphas are ad-hoc signed, not Apple notarized, and do not modify the stable signed Sparkle feed. Developer ID, notarization and production update keys still require owner configuration. The capability matrix records remaining feature and platform boundaries.
